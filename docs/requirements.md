# iqc-inspect — 進貨抽檢檢驗系統 需求文件

建立日期:2026-08-03
場景:LED 燈具(吸頂燈等)進貨/出貨抽檢,數位化現行紙本「產品出/進貨抽檢記錄」表單。

## 1. 檢驗流程(使用者提供)

```mermaid
flowchart TD
    Start([開始:收到進貨/抽檢通知]) --> Step1[1. 系統載入:選擇產品批號<br/><i>自動載入檢驗標準/公式/認證照片</i>]

    Step1 --> Step2[2. 光電測試:匯入積分球 PDF 報告<br/><i>自動解析功率、色溫、光通量等,人工確認</i>]
    Step2 --> Step3[3. 實體拆解:拍照並上傳零件照片<br/><i>系統同畫面並排認證照片供比對</i>]

    Step3 --> Check1{4. 系統自動綜合判定:<br/>各項數據與照片是否符合標準?}

    Check1 -- 判定不合格<br/>(含數據過低/功率異常/照片不符/外觀瑕疵等) --> Alert[5. 系統防呆警示:<br/><b>強制啟動第二件/箱二次拆檢</b>]
    Alert --> Step4[6. 執行二次檢驗:<br/>輸入第二件數據與照片]
    Step4 --> Check2{7. 判定第二次結果}

    Check1 -- 合格 --> Review
    Check2 -- 記錄完成 --> Review[8. 主管/複查人員審核<br/><i>系統自動高亮顯示所有異常項目</i>]

    Review --> Sign{9. 複查簽核}
    Sign -- 審核通過 --> Export[10. 系統自動套用固定格式<br/>匯出 Excel / PDF 完整檢驗報表]
    Sign -- 退件/判定批量不合格 --> Reject[11. 開立不良品異常單 / 退貨處理]

    Export --> End([結案歸檔])
    Reject --> End
```

註:原流程第 2 步為「人工輸入積分球數據」,經確認積分球軟體(Volnic FMS-6000)可直接匯出 PDF,改為 PDF 匯入自動解析(見 §4)。

## 2. 資料層級

```
檢驗單(一張表 = 一個貨櫃)
 ├─ 櫃號、封籤號、拆櫃日期、QC 日期
 └─ 型號檢驗 × 1~3(同櫃最多三個型號並排)── 各自綁定檢驗標準版本
     ├─ 型號層級檢驗項目值(人工數值、OK/NG 勾選)
     └─ 樣品 × 1~N(第 1 件;判不合格時「強制」加第 2 件 = 二次拆檢)
         ├─ 積分球 PDF(一顆燈一份,不同樣品是不同顆燈、數據不同)
         ├─ 拆解零件照片(與認證照片並排比對)
         └─ 單項判定結果
```

## 3. 檢驗項目的五種資料來源(依實際紙本表單歸納)

| 來源類型 | 說明 | 實例(紙本表單) |
|---|---|---|
| ① 自動帶入 | 產品主檔 + 公式計算的標準值 | 標稱功率 15W、色溫 4000K±500、功率上下限 13.5~16.5(=90%~110%)、光通量 1350~1500、AQL 允收數 |
| ② PDF 匯入 | 積分球報告解析,每樣品約 6 欄 | 色溫實測、功率實測、光通量、光效、PF、CRI |
| ③ 手動數值 | 現場量測人工輸入 | 淨重實稱、外箱 kg、噪音 dB、出貨數量、缺失數 |
| ④ OK/NG 勾選 | 目視與功能測試 | 實物+首件/BOM 表、目視外觀、簽核稿件核對、QR code、開關 5 次、雙切開關、點測/老化、壁切白光 5 秒切換 |
| ⑤ 自動判定 | 實測 vs 標準範圍,超標自動高亮 | 光效實測 133.0 > 上限 100 → 高亮(取代現行人工黃螢光筆) |

每個「檢驗項目」定義:名稱、資料來源類型、標準值/公式(容差)、判定規則。不同產品類別使用不同檢驗項目模板 → **新增產品/標準不改程式**。

## 4. 積分球 PDF 匯入(三層策略)

來源:Volnic FMS-6000「电光源测试报告」PDF(軟體直接匯出,固定版面)。

1. **優先**:pdfplumber 解析文字層,自動填入欄位(100% 保真)。已知風險:中文標籤可能因字型編碼呈亂碼 → 以「版面位置 + 數字模式」定位欄位,不依賴中文關鍵字。
2. **備援(第二期,未定案)**:文字層不可用時走 OCR;候選 PaddleOCR(本地、數字不幻覺)。待取得真實 PDF 樣本檔測試後決定。
3. **保底**:永遠可人工輸入/修正。

無論哪條路,解析結果都先進「人工確認畫面」才寫入判定。

## 5. 狀態機(後端強制,防呆核心)

```
draft(草稿)
  → data_entered(數據已錄入)
  → judged(已判定)
      ├─ 合格 ────────────────→ pending_review(待審核)
      └─ 不合格 → second_inspection(二次拆檢中)
                    └─(第二件數據齊)→ pending_review
  → pending_review → approved(已簽核)→ archived(已歸檔)
                   → rejected(退件)→ defect_ticket(異常單/退貨)→ archived
```

規則(伺服器端強制,非僅 UI):
- 判定不合格的型號,**沒有第二件樣品數據不允許進入 pending_review**。
- `approved` 之後的檢驗單**不可修改**,只能作廢重開。
- 每次狀態轉移與關鍵動作寫入 append-only 稽核軌跡(誰、何時、做了什麼)。

## 6. 角色

- **檢驗員**:建單、錄入數據、上傳 PDF/照片。
- **主管/複查人員**:審核(系統高亮異常項)、簽核/退件。

## 7. 報表匯出

- **Excel**:openpyxl 套用公司現行報表模板填值,格式與紙本一致。
- **PDF**:WeasyPrint(HTML/CSS + Jinja2 模板)。

## 8.3 檢驗標準兩層設計 + 產品主檔(2026-08-03 定案並實作)

- **類別標準**(spec_templates):每產品類別一份,定義檢驗項目 + 公式
  (規則以 `param`/`param_min`/`param_max` 引用參數,不寫死數字),版本化。
- **產品主檔**(products):型號的標稱參數(15W、1350~1500lm…)+
  **預期主機板標示字串** + 認證照(選填,不一定有)。
- 加型號=選產品:類別現行標準、參數、預期標示自動帶出並**快照**到檢驗單
  (主檔日後修改不影響歷史單)。新型號只建產品、不建標準;
  只有「檢驗方式改變」才發標準新版。
- 存量:30 份標準 Excel 由一次性遷移入庫(待用戶提供);增量:後台維護。

## 8.4 主機板標示比對關卡(2026-08-03 定案並實作)

核心比對:拆解後主機板上印的型號標示 vs 認證登記(產品主檔的預期字串)。

1. **送審關卡(後端強制)**:每型號必須有「主機板標示照」(photo.kind=marking)。
2. **簽核關卡(後端強制)**:主管逐型號勾「標示一致」(marking_confirmed),
   全數確認才放行 approve;勾選記入稽核軌跡。Excel 匯出維持簽核後才可。
3. **OCR 提示(僅供參考)**:Ollama `gemma4:e4b` 讀照片字串 → 程式做正規化
   精確比對 → 🟢一致/🟡不一致。模型只負責「讀」,比對是確定性程式邏輯,
   最終判斷永遠是主管勾選;Ollama 離線時靜默降級,流程不中斷。
   設定:`OLLAMA_URL`(demo 與正式部署皆與系統同機 localhost)。
   查證依據:通用視覺模型於 PCB 標示辨識尚不達產線判定等級(UniPCB 2026),
   故僅作輔助提示。

## 8.5 照片與檔案儲存設計(2026-08-03 定案)

檢驗員以手機/平板網頁直接拍照上傳,原圖 3~10MB,需控制儲存成本。

**儲存位置**:照片與 PDF 存磁碟 `data/uploads/`,資料庫只記檔名(不塞 blob)。

**上傳自動壓縮**:伺服器端 Pillow 處理——依 EXIF 轉正 → 長邊縮至 2000px → JPEG(品質 82)。
一張約 5MB → 0.3MB(降 10~20 倍),證據清晰度足夠;無法辨識的格式原樣保留。

**保存期限(用戶決策:短期保存)**:`.env` 的 `PHOTO_RETENTION_HOURS`(預設 24)。
排程每小時掃描,刪除「上傳滿時數 **且檢驗單已歸檔**」的照片(檔案+紀錄)。

> ⚠️ 設計保護:必須同時滿足「已歸檔」條件——否則主管隔天才審核的單,
> 照片會在審核前被清掉、流程斷裂。未歸檔的單照片一律保留,不受時數限制。
>
> ⚠️ 追溯取捨(已向用戶說明):照片清除後,若日後客訴/稽核需要影像證據將無法提供;
> 目前僅保留檢驗數據與稽核軌跡。若未來需要長期證據,調大 `PHOTO_RETENTION_HOURS`
> 即可(壓縮後保存數年成本極低),或於簽核時將照片嵌入 PDF 報告。

**積分球 PDF**:非照片、體積小,不在清除範圍(是判定依據的原始憑證)。

## 9. 分期

- **第一期(MVP)**:完整檢驗流程(建單→PDF 匯入→照片→判定→二次拆檢防呆→審核簽核→Excel/PDF 匯出)、標準版本化、稽核軌跡、角色登入。
- **第二期(預留)**:OCR 備援、AI 輔助照片比對(僅輔助不判定)、統計儀表板。
